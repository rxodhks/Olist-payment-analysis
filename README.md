# 결제 데이터 분석: 지표를 왜곡하는 함정 찾기

주문 약 10만 건의 이커머스 결제 데이터를 활용하여 Oracle에 직접 적재하고
지표를 왜곡하는 3가지 (주문 단위 고객 ID , JOIN Fan-Out , 할부로 인한 금액 불일치)를
SQL로 찾아 분석 기준을 설계한다.

> 진행 상황: 1단계(데이터 적재 · 정합성 검증) 진행 중 — 미션 0~3 완료

## 핵심 발견

| 발견 | 숫자 | 근거 쿼리 |
| --- | --- | --- |
| `customer_id`는 사람이 아니라 주문 단위 ID | ID당 최대 주문 1건 vs `customer_unique_id` 17건 | [`01_customer_id.sql`](sql/01_customer_id.sql) |
| 1:N 테이블을 그냥 JOIN하면 매출이 부풂 | 결제 합계 16,008,872 → 20,308,135 (+26.9%) | [`03_join_fanout.sql`](sql/03_join_fanout.sql) |
| 상품 금액과 결제액의 불일치는 할부와 관련 | 불일치율 할부 0.46% vs 일시불 0.027% | [`03_join_fanout.sql`](sql/03_join_fanout.sql) |

모든 쿼리는 오류 없이 실행되지만 출력되는 결과에서 차이가 발생한다.
고객 ID를 잘못 고르면 재구매율이 0%로 계산되고,
1:N 테이블을 일반 JOIN을 하게 되면 매출이 약 27% 부풀고,
결제액을 매출로 쓰면 할부 이자가 매출에 섞이는 현상이 발생한다.

## 분석 과정

각 장면은 문제 → 가설 → 검증 → 결론 순서로 정리합니다.

### 1. 원천 테이블 설계와 제약 검증 — [`00_create_raw.sql`](sql/00_create_raw.sql)
- **문제**: CSV 8개를 손실 없이 적재하고, 테이블 간 관계를 반드시 보장해야 했습니다.
- **설계**: 원천 값은 모두 VARCHAR2로 받고, 실제 데이터로 먼저 검증한 PK·FK·CHECK만 걸었습니다.
- **검증**: 문자열(VARCHAR2)로 받은 덕분에 0으로 시작하는 우편번호 23,995건이 보존됐습니다.
  상품 → 카테고리 번역표에 FK를 걸려다가 번역이 없는 카테고리 2종(상품 13개)을 발견해 FK를 제외했습니다.
- **결론**: 8개 테이블의 행 수가 원천과 모두 일치했습니다. FK 덕분에 적재 순서(부모 → 자식)도 강제됐습니다.

### 2. 고객 ID 함정 — [`01_customer_id.sql`](sql/01_customer_id.sql)
- **문제**: 재구매 분석에는 customer_id와 customer_unique_id 중 무엇을 써야 할까?
- **처음 가설**: 같은 정보로 다시 가입하면 아이디는 달라도 유니크 아이디는 같으니, customer_id를 써야 한다고 판단했습니다.
- **검증**: ID별 최대 주문 수를 세어 보니 customer_id는 1건, customer_unique_id는 17건이었습니다(2건 이상 주문한 사람 2,997명).
- **결론**: customer_id는 주문마다 새로 발급되는 ID라서, 이를 쓰면 재구매율이 0%가 됩니다.
  쿼리 작성 그리고 출력되는 결과를 통해 처음 가설이 틀렸음을 확인하고, 사람 단위 지표는 customer_unique_id로 계산하기로 했습니다.

### 3. 실행 계획 읽기 — [`01_customer_id.sql`](sql/01_customer_id.sql)
- **문제**: 위 쿼리에서 비용이 가장 큰 단계는 어디일까?
- **검증**: Cost는 자식 단계를 포함한 누적값이라 단계별로 빼서 계산했습니다.
  스캔 약 1,060, HASH JOIN 582, HASH GROUP BY 2,214로, 병목은 풀 스캔이 아니라 GROUP BY였습니다.
- **결론**: "고객 행 1개 = 주문 1건"이라는 전제를 이용하면 JOIN을 없애 Cost를 3,857에서 1,257로 줄일 수 있습니다.

### 4. 분석 범위 결정 — [`02_scope.sql`](sql/02_scope.sql)
- **문제**: 어떤 기간과 어떤 상태의 주문을 분석에 쓸까?
- **처음 시도**: 월(MM)만 잘라 집계했더니 서로 다른 해가 합쳐져 모든 달이 4,000건 이상으로 보였습니다.
- **검증**: 연-월로 다시 집계하니 2016-09 4건, 2016-11 0건, 2016-12 1건, 2018-09 16건, 2018-10 4건이었습니다.
- **결론**: 이 달들은 수요가 아니라 데이터 수집 시작·종료 때문에 적은 것으로 판단해,
  연속성이 보장되는 2017-01 ~ 2018-08만 분석합니다.
  취소·이용 불가 주문은 구매로 보지 않고, delivered 주문(약 97%)만 사용합니다.

### 5. JOIN 부풀림 — [`03_join_fanout.sql`](sql/03_join_fanout.sql)
- **문제**: 주문·상품·결제 테이블을 일반 JOIN해서 결제액을 합산하면 맞을까?
- **검증**: 결제 테이블 단독 합계는 16,008,872였지만, JOIN 결과는 20,308,135로 26.9% 부풀었습니다.
  상품 2개·결제 2건인 주문은 JOIN하면 4행이 되어 결제액이 두 번씩 더해졌습니다.
  반대로 상품이 없는 주문의 결제 830행은 INNER JOIN에서 빠졌습니다.
- **결론**: 1:N 관계인 테이블은 JOIN 전에 주문 단위로 먼저 집계해 주문당 1행(98,665행)으로 만든 뒤 합치는 과정으로 진행했습니다.

### 6. 금액 불일치 원인과 매출 정의 — [`03_join_fanout.sql`](sql/03_join_fanout.sql)
- **문제**: 상품 금액과 결제액이 1 BRL 넘게 다른 주문 249건은 왜 생겼을까?
- **가설**: 할부로 결제하면 이자가 붙어 결제액이 상품 금액보다 커질 것이다.
- **검증**: 249건 중 232건은 결제액이 더 컸고, 그중 229건이 할부였습니다.
  불일치율은 할부 0.46%, 일시불 0.027%로 약 17배 차이가 났습니다.
- **결론**: 매출은 할부 이자 등 결제 조건의 영향을 받지 않는 상품 금액(가격 + 배송비) 기준으로 정의했습니다.
